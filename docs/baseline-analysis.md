# بررسی اولیه پروژه Shopping Cart

این بررسی در تاریخ ۳۰ اوت ۲۰۲۶ و روی نسخه اولیه پروژه با commit زیر انجام شد:

```text
5658ddbbff70f6eab3b35d2cd5ef6c8dfc036219
```

هدفم در این مرحله این بود که قبل از نوشتن تست یا تغییر رفتار برنامه، اول بفهمم پروژه فعلی دقیقاً چه کاری انجام می‌دهد و تست‌های موجود چقدر از آن را پوشش داده‌اند.

## اجرای پروژه قبل از هر تغییری

پروژه اولیه فایل `pom.xml` یا تنظیمات Gradle نداشت و فقط فایل تنظیمات IntelliJ داخل آن بود. برای اینکه اولین اجرا واقعاً روی نسخه دست‌نخورده انجام شود، یک POM موقت بیرون از مخزن و در `/tmp` ساختم. خروجی build هم در `/tmp/swe-lab3-untouched-target` تولید شد؛ بنابراین اجرای اولیه چیزی داخل repository ایجاد یا ویرایش نکرد.

فرمان اجرا:

```bash
mvn -f /tmp/swe-lab3-untouched-runner-pom.xml clean test
```

نتیجه‌ای که گرفتم:

```text
3 source files compiled
1 test source file compiled
Tests run: 4, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

بعد از اجرا، `git status` همچنان clean بود. همچنین hash فایل تست اولیه را ثبت کردم تا در پایان آزمایش بتوانیم مطمئن شویم این فایل تغییر نکرده است:

```text
Test/ShoppingCartTest.java
661e5e2cae9ef018fd61f944ea09245f7be38706
```

روی سیستم فعلی OpenJDK 23.0.1 و Maven 3.9.9 نصب است. برای اینکه اجرای محلی و CI به یک نسخه پایدار و مشترک وابسته باشند، Java 17 را به‌عنوان نسخه هدف build انتخاب کردم. Gradle روی سیستم نصب نبود و با توجه به کوچک بودن پروژه، Maven انتخاب ساده‌تری بود.

## چیزی که از کد اولیه فهمیدم

کلاس اصلی پروژه `ShoppingCart` است. کالاها داخل یک `HashMap<String, Double>` نگهداری می‌شوند؛ یعنی نام کالا کلید و قیمت آن مقدار است. یکی از نتایج این انتخاب این است که اگر دو کالا با یک نام اضافه شوند، مقدار دوم جای مقدار اول را می‌گیرد و تعداد آیتم‌ها زیاد نمی‌شود.

رفتار متدهای فعلی به این شکل است:

- `addItem` نام و قیمت را بدون validation داخل Map قرار می‌دهد.
- `removeItem` اگر نام وجود داشته باشد آن را حذف می‌کند و `true` برمی‌گرداند؛ در غیر این صورت `false` می‌دهد.
- `getTotal` همه قیمت‌ها را با نوع `double` جمع می‌کند.
- `getTotalWithDiscount` در کد فعلی برای مجموع بزرگ‌تر یا مساوی ۱۰۰، ده درصد تخفیف می‌دهد.
- `getItemCount` همان اندازه Map را برمی‌گرداند.
- متد `updateItemPrice(String, int)` وجود دارد، اما بدنه‌اش خالی است. امضایی که صورت آزمایش خواسته از `double` برای قیمت جدید استفاده می‌کند.

کلاس `Item` فقط نام و قیمت را نگه می‌دارد، ولی در پیاده‌سازی فعلی `ShoppingCart` اصلاً از آن استفاده نشده است. کلاس `Main` هم کد نمونه تولیدشده توسط IntelliJ است و ارتباطی با منطق سبد خرید ندارد.

## تست‌های موجود

چهار تست فعال پیدا کردم:

1. افزودن یک کتاب با قیمت ۵۰ و بررسی تعداد و مجموع؛
2. حذف یک خودکار موجود و بررسی مقدار بازگشتی، تعداد و مجموع؛
3. بررسی تخفیف برای مجموع دقیقاً ۱۰۰؛
4. بررسی تخفیف برای مجموع ۱۲۰.

سه تست مربوط به `updateItemPrice` هم در فایل تست وجود دارند، اما کامنت شده‌اند و در اجرای فعلی حساب نمی‌شوند.

نکته جالب این است که نام تست مرز ۱۰۰، `testDiscountAtBoundary_WRONG` است و انتظار دارد خروجی ۹۰ باشد. این انتظار با متن PDF سازگار نیست، چون طبق صورت آزمایش مجموع دقیقاً ۱۰۰ نباید تخفیف بگیرد. در این مرحله آن را تغییر ندادم، چون اصلاحش باید بعداً با یک تست Red واقعی و در Task باگ‌ها انجام شود.

## جاهایی که هنوز تست نشده‌اند

در این مرحله این موارد را باگ قطعی در نظر نگرفتم؛ فقط جاهایی هستند که یا تست ندارند یا رفتارشان باید دقیق‌تر مشخص شود:

- حذف کالایی که وجود ندارد و حذف چندباره؛
- اجرای `getTotalWithDiscount` برای مجموع کمتر از ۱۰۰؛
- مرز دقیق ۱۰۰ بر اساس متن PDF؛
- نام `null` یا نام خالی؛
- قیمت صفر، منفی، `NaN` یا بی‌نهایت؛
- قیمت‌های اعشاری و اعداد خیلی بزرگ؛
- اضافه کردن چند کالا با نام یکسان؛
- تغییر نکردن وضعیت سبد در حالت خطا؛
- قرارداد دقیق `updateItemPrice`.

برای اینکه تاریخچه TDD واقعی بماند، در Task 1 برای این موارد تست جدیدی اضافه نکردم.

## نتیجه Mutation Testing اولیه

PIT را با این فرمان اجرا کردم:

```bash
mvn --batch-mode --no-transfer-progress test-compile \
  org.pitest:pitest-maven:mutationCoverage
```

PIT برای `ShoppingCart` تعداد ۱۱ mutant ساخت. ۹ مورد توسط تست‌ها کشته شدند، هیچ mutant پوشش‌داده‌شده‌ای زنده نماند و ۲ مورد اصلاً به وسیله تست‌ها اجرا نشدند.

```text
Total mutants: 11
Killed: 9
Survived: 0
No coverage: 2
Mutation score: 81.82% (9/11)
Test strength for covered mutants: 100% (9/9)
```

دو mutant بدون پوشش دقیقاً با شکاف‌هایی که در بررسی دستی دیده بودم مرتبط هستند:

- مقدار بازگشتی مسیر بدون تخفیف در `getTotalWithDiscount`؛
- مقدار بازگشتی مسیر حذف کالای ناموجود در `removeItem`.

فعلاً برای کشتن این دو mutant تست اضافه نکردم، چون این کار نتیجه baseline را تغییر می‌داد. این موارد ورودی مناسبی برای Taskهای TDD بعدی هستند.

گزارش PIT در `target/pit-reports/` قرار می‌گیرد.
