# گزارش باگ‌های پنهان Shopping Cart

این فایل هم‌زمان با چرخه‌های TDD تکمیل می‌شود تا خروجی Red و Green از روی تاریخچه واقعی Git قابل بررسی باشد.

## باگ اول: اعمال تخفیف روی مرز دقیق ۱۰۰

### چیزی که انتظار داشتیم

طبق صفحه دوم PDF، تخفیف ده‌درصدی فقط وقتی اعمال می‌شود که مجموع **بیشتر از ۱۰۰** باشد. بنابراین برای مجموع دقیقاً ۱۰۰، خروجی `getTotalWithDiscount` باید همان ۱۰۰ باقی بماند.

### رفتاری که دیدیم

با افزودن دو کالا به قیمت‌های ۴۰ و ۶۰، متد مقدار ۹۰ را برمی‌گرداند. شرط پیاده‌سازی `total >= 100` بود و مرز ۱۰۰ را هم وارد مسیر تخفیف می‌کرد.

تست اولیه پروژه نیز همین رفتار اشتباه را انتظار داشت و نام آن `testDiscountAtBoundary_WRONG` بود. از طرفی تغییر تست‌های اولیه ممنوع اعلام شده بود. این تناقض در checkpoint به کاربر گزارش شد و کاربر صریحاً اجازه داد همان assertion اشتباه اصلاح و این استثنا مستند شود.

- hash تست اولیه: `661e5e2cae9ef018fd61f944ea09245f7be38706`
- hash تست بعد از اصلاح مورد تأیید: `a4742604ce5914f47ab5b98fdc4a95dbeb8aaa4b`

### Red

در commit `da3ac2d` نام تست مرزی اصلاح شد و مقدار مورد انتظار از ۹۰ به ۱۰۰ تغییر کرد. اجرای متمرکز:

```bash
mvn --batch-mode --no-transfer-progress \
  -Dtest=ShoppingCartTest#testDiscountAtBoundary test
```

خروجی اصلی شکست:

```text
Tests run: 1, Failures: 1, Errors: 0, Skipped: 0
expected: <100.0> but was: <90.0>
BUILD FAILURE
```

### Green

علت ریشه‌ای فقط عملگر مقایسه بود. در commit `5991721` شرط `>= 100` به `> 100` تغییر کرد و هیچ منطق دیگری دست نخورد.

```text
Focused test: 1 run, 1 passed
Full suite: 4 run, 4 passed
BUILD SUCCESS
```

تست‌های قبلی این باگ را پیدا نکرده بودند، چون تست مرزی موجود خودش قرارداد اشتباه را تثبیت می‌کرد. تست مجموع ۱۲۰ نیز فقط مسیر بالاتر از مرز را پوشش می‌داد.

### Refactor

نیازی نبود؛ اصلاح یک‌کاراکتری روشن و حداقلی است.

## باگ دوم: ناپایداری مجموع قیمت‌های اعشاری

### چیزی که انتظار داشتیم

PDF روی پایداری محاسبات اعشاری تأکید دارد. برای دو قیمت واقعی ۰٫۱ و ۰٫۲، مقدار قابل مشاهده مجموع باید با عدد اعشاری ۰٫۳ یکسان باشد.

### رفتاری که دیدیم

پیاده‌سازی اولیه قیمت‌ها را مستقیماً با `double` جمع می‌کرد و مقدار زیر به دست می‌آمد:

```text
expected: <0.3> but was: <0.30000000000000004>
```

تست‌های قبلی فقط قیمت‌های صحیح ۵، ۴۰، ۵۰، ۶۰ و ۱۲۰ را استفاده می‌کردند؛ به همین دلیل خطای نمایش دودویی اعشار آشکار نشده بود.

### Red

در commit `50fcedf` تست `decimalItemPricesHaveStableTotal` به فایل جداگانه `ShoppingCartHiddenBugsTest` اضافه شد.

```text
Focused test: 1 run, 1 failed
expected: <0.3> but was: <0.30000000000000004>
BUILD FAILURE
```

### Green

علت ریشه‌ای، جمع مستقیم مقادیر پولی با `double` بود. در commit `56a9d4d` جمع داخلی با `BigDecimal.valueOf` انجام شد و فقط نتیجه نهایی به نوع public فعلی یعنی `double` تبدیل شد. به این ترتیب API پروژه تغییر نکرد و rounding دلخواهی نیز وارد نشد.

```text
Focused test: 1 run, 1 passed
Full suite: 5 run, 5 passed
BUILD SUCCESS
```

### Refactor

تغییر ساختاری جداگانه‌ای لازم نبود. تبدیل کل storage به `BigDecimal` برای رفع همین خطا بیش از حد گسترده بود و به Taskهای اعتبارسنجی آینده هم اثر می‌گذاشت.

## باگ سوم: ناپایداری محاسبه خود تخفیف

### چیزی که انتظار داشتیم

پایدار شدن جمع در باگ دوم کافی نیست؛ PDF مشخصاً محاسبات اعشاری تخفیف را هم مطرح می‌کند. برای یک کالا با قیمت ۱۰۰٫۲۲، ده درصد تخفیف باید نتیجه قابل مشاهده ۹۰٫۱۹۸ را بسازد.

### رفتاری که دیدیم

مجموع برای یک کالا همان ۱۰۰٫۲۲ بود، اما ضرب مستقیم آن در `0.9` این خروجی را تولید کرد:

```text
expected: <90.198> but was: <90.19800000000001>
```

این با باگ دوم مستقل است: باگ دوم در حلقه جمع `getTotal` رخ می‌داد، اما این مورد با تنها یک کالا و در عمل ضرب داخل `getTotalWithDiscount` دیده می‌شود. تست‌های قبلی از قیمت ۱۲۰ استفاده می‌کردند که حاصل ضرب آن در این نمایش خاص، همان ۱۰۸ مورد انتظار بود.

### Red

در commit `cbfd271` تست `decimalDiscountHasStableResult` اضافه شد و به‌تنهایی شکست خورد.

```text
Focused test: 1 run, 1 failed
expected: <90.198> but was: <90.19800000000001>
BUILD FAILURE
```

### Green

در commit `e6bb97d` فقط محاسبه ده درصد تخفیف با `BigDecimal.valueOf` انجام شد. شرط تخفیف و نوع خروجی public تغییر نکردند.

```text
Focused test: 1 run, 1 passed
Full suite: 6 run, 6 passed
BUILD SUCCESS
```

### Refactor

Refactor جداگانه‌ای انجام نشد. بیرون کشیدن یک abstraction برای فقط یک ضریب ثابت، در این اندازه پروژه خوانایی بیشتری ایجاد نمی‌کرد.

## جمع‌بندی Task 2

سه باگ با سه ورودی مستقل اثبات شدند:

1. مجموع دقیق ۱۰۰: اعمال اشتباه تخفیف به دلیل `>=`؛

3. قیمت ۱۰۰٫۲۲: خطای ضرب دودویی در محاسبه تخفیف.

هر مورد Red و Green جداگانه دارد و پس از هر Green، کل مجموعه تست‌ها دوباره اجرا شده است.
